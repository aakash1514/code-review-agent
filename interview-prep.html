Automated PR Review System

FastAPI · React · Qdrant · GitHub App · Groq · Hugging Face

Mobile interview cheat sheet

Be accurate in the interview. This repository uses Groq for reasoning and Hugging Face for embeddings. I found no Bedrock, Terraform, ECS/Fargate, GitHub Actions, or monitoring implementation in this snapshot.

30-second explanation

GitHub sends a signed webhook when a pull request opens or changes. FastAPI verifies it, deduplicates by commit SHA, and schedules a background review. Each changed file gets targeted AST and vector context, then four specialist agents run concurrently. Their findings are merged, deduplicated, ranked, synthesized into a PR comment, and converted into a GitHub status check. The React dashboard streams progress and lets an authenticated repository writer approve or block the result.

Main orchestration: api/webhook.py, pipeline/runner.py, rag/retriever.py.

2. The four agents and parallelism
  • Security injection, auth, secrets, crypto, SSRF, unsafe input.
  • Architecture robustness, complexity, coupling, validation, edge cases.
  • Test coverage identifies testable risk from the diff; it does not inspect the actual test suite.
  • Documentation missing or misleading docs and comments.

Implementation: pipeline/runner.py uses asyncio.gather plus run_in_executor.

Precise answer: orchestration is async, but agents make synchronous requests calls in thread-pool workers. It is not pure async HTTP.

tasks = [_run_one(fn) for fn in AGENT_FUNCTIONS]
return await asyncio.gather(*tasks)

“4x faster” caveat: there is no benchmark in the repository. The theoretical comparison is sequential four-agent execution, about 4T, versus parallel execution near T plus overhead.

3. Hybrid RAG: AST graph + Qdrant

AST knowledge graph

rag/knowledge_graph.py parses Python with ast, records functions, calls, and dependents. It answers: “What does this function call?” and “Who depends on it?”

Qdrant vector search

rag/indexer.py chunks code, creates 384-dimensional Hugging Face embeddings, and stores repository-tagged vectors. Queries filter by repo to prevent cross-repository leakage.

Context reduction

rag/retriever.py caps the context at 8,000 characters, roughly around 2K tokens depending on the tokenizer. It includes up to 10 graph entries and 5 similar snippets.

Honest caveat: the exact “15K to 2K tokens” improvement is not benchmarked in this codebase.

4. GitHub App, OAuth, and status checks

App auth: create a short-lived App JWT from the private key, exchange it for an installation token, cache it, and refresh before expiry. Used for PR files, comments, statuses, contents, and permission checks.

Human auth: GitHub OAuth identifies the dashboard user. A random state protects the OAuth round trip; a server-side SQLite session lasts seven days.

Status:

  • pending when review starts
  • failure when a CRITICAL finding exists
  • success when there are no CRITICAL findings
  • failure when the pipeline fails

The context name is ai-code-review. See tools/github_tools.py, api/auth.py, and pipeline/hitl_gate.py.

5. Failure handling and cost control

Agent failure

Each agent has a 45-second logical timeout. Timeout, exception, model unavailability, or two invalid JSON responses become an error-bearing AgentReport; other agents continue.

Subtlety: cancelling the executor wait does not forcibly kill a synchronous thread already making an HTTP request.

Duplicate and stale commits

pipeline/job_store.py rejects duplicate pending/running/complete jobs for the same repo and SHA. A newer SHA becomes the latest; an older completed run is discarded before posting its final result.

Rate limits

Groq retries HTTP 429 and falls back between reasoning and light models. Embeddings retry three times. GitHub requests have timeouts, but no dedicated 429/backoff policy.

Cost controls

Cheaper model for test/documentation, bounded context, token limits, retries, deduplication, timeouts, and repository-scoped retrieval. No explicit dollar budget, token ledger, global concurrency limit, or circuit breaker.

6. Twenty likely interview questions

1. How is the webhook verified?

HMAC-SHA256 over the raw body with hmac.compare_digest; require the sha256= prefix. See api/webhook.py.

2. Which events are supported?

pull_request.opened, pull_request.synchronize, and pushes to the default branch for re-indexing.

3. Why return quickly from the webhook?

GitHub delivery requests should not wait for LLM and GitHub API calls. The handler only validates, deduplicates, writes SQLite, and schedules the background task.

4. How do the agents run in parallel?

asyncio.gather awaits four executor-backed synchronous functions. Files are sequential; agents within one file are concurrent.

5. What was 4x measured against?

Nothing in this repository. It is a theoretical comparison with sequentially running four independent agents, not a measured claim.

6. What if an agent times out?

A timeout report with no findings is returned, the other agents continue, and the dashboard receives an error event.

7. How are duplicate webhooks handled?

Atomic SQLite check by (repo, commit_sha); pending, running, and complete duplicates are skipped. Failed jobs can retry.

8. How is a newer commit handled?

The latest SHA is stored per PR. An older run checks is_stale_sha before posting a comment/status.

9. How are GitHub App tokens obtained?

Sign a nine-minute App JWT, exchange it for an approximately one-hour installation token, cache it, and refresh five minutes before expiry.

10. How is the human user authenticated?

GitHub OAuth with a random state; the user token identifies the person, and a server-side SQLite session is used by the dashboard.

11. Who can approve or block?

A valid dashboard session plus GitHub write/admin permission on that repository. The backend checks permission before changing the status.

12. What determines the final status?

At least one CRITICAL finding means failure; otherwise success. HIGH findings are surfaced but do not automatically block.

13. Why combine an AST graph and vectors?

The graph gives exact structural relationships; vectors find semantically similar patterns. They complement each other.

14. How is context bounded?

Retriever output is capped at 8,000 characters, with bounded graph and similarity-result counts. Exact 15K-to-2K improvement is not measured here.

15. What models are really used?

Groq for all reasoning and synthesis; Hugging Face for embeddings. No Bedrock client exists in this snapshot. See config.py and tools/model_client.py.

16. How do you handle malformed LLM JSON?

Parse, retry once with a JSON-only instruction, then return an error-bearing report instead of crashing the pipeline.

17. What if synthesis fails?

A deterministic Markdown fallback lists findings by severity, with locations and suggestions. See pipeline/synthesizer.py.

18. How are findings deduplicated?

By file, category, and a normalized snippet hash. The strict key favors avoiding false-positive deletion of distinct findings.

19. What is the test agent’s limitation?

It reasons from the diff and does not fetch the real test suite, so it reports testable risk rather than proving a test is missing.

20. Is this production-ready on ECS?

Not as shown. SQLite is local, WebSockets are unauthenticated, GitHub 429 handling is incomplete, and Terraform/ECS/Docker/monitoring are absent. I would add a queue, shared datastore, secrets manager, container deployment, health checks, observability, and rate limiting.

7. What to defend — and what to admit
Defend: fast webhook acknowledgment, raw-body HMAC verification, durable job state, duplicate suppression, stale-commit protection, structured Pydantic findings, hybrid retrieval, repository isolation, and graceful degradation.

Admit clearly

  • Bedrock is not implemented; Groq is used.
  • Terraform, ECS/Fargate, Docker, CI/CD, and monitoring are not in this repository.
  • The 4x speedup is not benchmarked.
  • The 15K-to-2K reduction is not instrumented as an experiment.
  • Test coverage analysis does not inspect test files.
  • AST call-graph coverage is mainly Python; JS/TS use vector chunks only.
  • Local SQLite is not a suitable shared store for multiple ECS tasks.
  • WebSocket access currently has no authentication.
  • GitHub API rate-limit handling needs improvement.

Final answer to memorize

“This is a FastAPI GitHub App that verifies signed PR webhooks, deduplicates reviews by commit SHA, and runs four specialized review agents concurrently per changed file. It combines AST call/dependency context with repository-scoped Qdrant similarity search. Findings are structured, deduplicated, ranked, synthesized into a PR comment, and converted into a GitHub status: CRITICAL findings fail the check. React receives live WebSocket progress and supports authenticated human overrides. In this repository, the reasoning provider is Groq and embeddings use Hugging Face; Bedrock, Terraform, ECS/Fargate, CI/CD, and production monitoring are planned or external, not implemented here.”
